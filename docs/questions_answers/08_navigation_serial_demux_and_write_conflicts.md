# 08 导航侧做串口分流时，写串口会不会冲突

## 结论

会不会冲突，取决于“谁拥有串口”。

### 不会冲突的情况

只有一个进程打开串口，并且所有写操作都在这个进程里串行化。

### 一定会冲突的情况

多个进程同时打开同一个串口设备并各自写。

## 当前仓库的桥接程序是怎么避免冲突的

`gimbal_ros2_bridge` 里所有串口读写都在同一个进程里完成，而且写串口前用了同一个 `serial_mutex_`。

见：

- 写串口加锁：`diagnostics/gimbal/gimbal_ros2_bridge.cpp:204-214`
- 读串口加锁：`diagnostics/gimbal/gimbal_ros2_bridge.cpp:259-272`

所以在“只有 bridge 独占串口”的前提下，桥接程序内部不会出现多线程写冲突。

## 你的导航方案怎么落地才对

你说的方案本质上是“导航进程成为串口唯一拥有者”，这是可行的，但要满足两个条件：

1. 串口只由导航这个单进程打开
2. 自瞄包和导航包都在这个进程里统一收发

## 推荐结构

建议导航侧做成一个单独的“串口复用器”：

### 接收方向

1. 从串口读原始字节流
2. 按包头和长度识别包类型
3. 如果是 `GimbalToVision` 包，就发布到 `/gimbal_to_vision`
4. 如果是导航自己的包，就发到导航原有 topic

### 发送方向

1. 订阅 `/visionToGimbal`
2. 订阅导航自己的发送 topic
3. 所有待发包进入同一个发送队列
4. 由同一个串口发送线程顺序写出

## 当前仓库还没做的部分

当前仓库提供的 `gimbal_ros2_bridge` 只处理自瞄这一路协议，没有做：

- 导航原有串口包的分流
- 自瞄包和导航包的统一仲裁
- 多种协议共享一个串口的总调度

也就是说，当前 bridge 不是“导航总线复用器”，只是“自瞄协议桥”。

## 仲裁问题

如果导航和自瞄都可能主动发包，就算在同一个进程里，也还要再定一个策略：

- 哪个 topic 优先级更高
- 是立即发送还是进队列
- 是否允许覆盖旧命令
- 是否需要节流

否则虽然不会出现“字节级写冲突”，但仍然会出现“语义级命令打架”。

## 推荐规则

最简单的规则可以是：

1. 串口只有一个 owner 进程
2. 自瞄和导航分别进两个 topic
3. 发送前统一封包
4. 统一串行写
5. 若两个模块都能控制云台，必须再加优先级仲裁

## 最终回答

### “这里写串口会有冲突吗”

如果是一个进程独占串口并统一发送，不会有底层写冲突。

如果是两个进程都开 `/dev/ttyACM0`，就会冲突。

### “导航应该把原来的串口功能做分流吗”

应该，而且最好把它做成串口唯一 owner，这样整个系统最清晰。
